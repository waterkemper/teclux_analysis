# Commit F8 atômico, concorrência, idempotência e auditoria da Manutenção de Preços interna

Status: ready-for-agent
Label: ready-for-agent

## Problem Statement

A sessão local de propostas (terceiro spec) produz um comando canônico revisável, mas nunca grava nada — nenhuma linha de `colunasprecos`, `precos`, `produtoscargos`, `produtos` ou `caracteristicas` é alterada até este ponto. O ERP precisa de uma confirmação F8 que aplique esse lote inteiro de forma atômica (tudo ou nada), autorizada uma única vez por um Gerente de Estoque, protegida contra alterações concorrentes de outro Laravel ou do próprio Delphi, idempotente diante de repetição de rede, e auditável o suficiente para reconstruir quem operou, quem autorizou, qual Filial, quais filtros e cada diferença individual — sem tocar Marketplace nem reprecificar Orçamentos, Contratos ou Vendas já persistidos.

O Delphi legado não comprova uma transação abrangente única (há `Perpetrar` disperso entre grupos e dentro de laços), então uma falha tardia pode deixar grupos anteriores aplicados — esse comportamento não deve ser reproduzido.

## Solution

Construir um módulo de **Commit Atômico da Manutenção Interna** com uma única operação: dado o comando canônico do spec anterior, o Operador da sessão e uma prova de autorização sensível, aplicar o lote inteiro numa única transação e devolver o resultado. Antes de qualquer escrita, validar autorização, escopo de Filial, forma do payload e invariantes de domínio; bloquear os alvos físicos em ordem determinística; conferir a revisão esperada de cada um. Qualquer divergência aborta o lote inteiro com a lista completa de conflitos — nada é aplicado parcialmente e nada é sobrescrito silenciosamente.

A confirmação usa exatamente a prova sensível de Gerente de Estoque já definida para este módulo, obtida uma única vez para o lote inteiro (nunca por célula). Idempotência usa `request_id` (UUID) e hash canônico do payload: repetir a mesma dupla devolve o resultado anterior sem reexecutar nada; reusar o `request_id` com payload diferente é rejeitado. Auditoria combina um cabeçalho interno próprio (correlacionando UUID, hash, Operador, Autorizador, Filial efetiva, filtros normalizados, horário, estado e contagens) com as triggers append-only já existentes nas cinco tabelas afetadas — sem duplicar manualmente os diffs e sem qualquer chamada a Marketplace. Depois do commit, a tela conserva os filtros e roda F6 de novo; nenhum evento é publicado para Vendas, e nenhum documento já gravado é reprecificado.

## User Stories

1. As a Usuário de Estoque, I want F8 to apply my entire prepared batch atomically, so that a partial write never leaves the catalog in an inconsistent state.
2. As a Usuário, I want a single sensitive authorization for the whole batch, not one per row or per cell, so that reviewing and confirming a large batch stays practical.
3. As a Gerente de Estoque, I want to confirm with just my own password when I am the session's operator, so that I don't need a second person for my own authorized change.
4. As a Usuário who is not a Gerente de Estoque, I want the system to require login and password of an authorized Gerente, so that elevated changes always have a real authorizer.
5. As a Usuário, I want the batch rejected outright if the resulting authorizer does not actually hold the Gerente de Estoque profile, so that the check is never merely cosmetic.
6. As a Usuário, I want any failure at any point during the commit to roll back every change in the batch, so that "almost committed" never happens.
7. As a Usuário, I want concurrent commits touching overlapping targets to have exactly one winner, with the other receiving the complete list of conflicting targets and their expected/actual revisions, so that I always know precisely what changed under me.
8. As a Usuário, I want no automatic overwrite when a conflict is detected, so that I explicitly decide how to reconcile before trying again.
9. As a Usuário, I want repeating the exact same confirmation (same request identity and same payload) to return the same result without creating new changes or new log entries, so that a network retry is safe.
10. As a Usuário, I want reusing the same request identity with a different payload rejected, so that request identities cannot be abused to smuggle a different batch through as a "retry".
11. As a Usuário, I want a Coluna de Preço Valor of zero to physically remove the existing configuration for that identity, and a non-zero Valor to insert or update it, exactly as the proven legacy rule, so that clearing a price behaves the same way it always has.
12. As a Usuário, I want linking a Promoção to a Característica + Faixa to persist as one single mutation shared by every visual row of that identity, not one write per row, so that the catalog stays consistent with how the concept is actually modeled.
13. As a Usuário, I want unlinking a Promoção to only null the link, never touching the Promoção's own registration or the promotional column's Valor/Validade, so that unrelated data survives an unlink.
14. As a Usuário, I want to be warned, not silently corrected, when removing a promotional Valor leaves a Promoção link without an effective price, so that I notice an inconsistent configuration instead of it being hidden from me.
15. As a Usuário, I want an empty Desconto por Cargo to persist as zero, never as a silent deletion, with physical exclusion remaining its own explicit action reused from the existing Cadastro de Produtos flow, so that Cargo behavior matches its proven semantics.
16. As a Usuário, I want batch Cargo mutations rejected outright when Preços por Cargo is disabled for the relevant Filial, so that a disabled feature can never be mutated through this path.
17. As a Usuário, I want produtos/caracteristicas field changes (markup, grupo, classe, marca, Faixa assignment) checked against their existing revision tokens like every other target in the same batch, so that concurrency protection is uniform across every table this commit touches.
18. As an auditor, I want a batch header correlating request identity, payload hash, Operador, Autorizador, effective Filial, normalized filters, timestamp, final state and counts, separate from Marketplace's own audit trail, so that Estoque price changes are reconstructible on their own.
19. As an auditor, I want per-table before/after diffs sourced from the existing append-only triggers, correlated by the same request identity, not duplicated by a manual diff computation, so that there is exactly one source of truth for what changed.
20. As an auditor, I want Operador and Autorizador recorded distinctly even when they are the same person, so that self-authorization is still explicit in the trail.
21. As an auditor, I want rejected attempts to produce no diffs, sensitive-authorization attempts to land in the sensitive-operation log, and technical failures to land in structured logs without any credential, so that logs stay both complete and safe.
22. As a Usuário, I want the page to keep my current filters and re-run F6 after a successful commit, so that I immediately see the collection reflecting the new corrente prices.
23. As a Usuário, I want a failed post-commit refresh to never undo or invalidate an already-successful commit, so that a display hiccup can't masquerade as a lost write.
24. As a developer of Orçamentos, Contratos or a future Frente de Caixa, I want this commit to never call, enqueue or publish anything toward Vendas, so that price maintenance stays a pure catalog operation and documents keep resolving price on demand instead of being reprecificados retroactively.
25. As the business, I want zero calls to any Marketplace service, repository, job or publication path from this commit, so that the two contexts never regress each other.
26. As the business, I want pré-validação and gravação to complete within the already-fixed performance budget (15 seconds, except an explicitly reported concurrent block), so that a large batch commit stays usable.
27. As the business, I want this feature released to every Usuário who already has module access, all at once, after a manual homologation of at least one real batch, with no pilot list or feature flag, so that rollout matches the already-agreed release strategy.
28. As a maintainer, I want existing unitary price/Cargo write services' proven SQL/business logic reused as internal collaborators inside this single transaction, not looped as independently-transacted public calls, so that atomicity is real, not simulated by many small transactions.
29. As a maintainer, I want revision tokens reused where they already exist (produtos, caracteristicas) and canonically signed where they don't (colunasprecos, produtoscargos, precos — including expected absence for insert-when-missing cases), so that optimistic concurrency covers every table this commit touches without inventing a redundant scheme for tables that already have one.
30. As a maintainer, I want no price cache introduced by this specification, and any future cache elsewhere to be required to key on Produto, Filial, Faixa/tabela, Cliente/Cargo, Promoção/data and catalog revision, so that a future cache cannot silently violate the freshness guarantees this module protects today.

## Implementation Decisions

- Confirm via a Laravel F8 action (the equivalent of the legacy F5), invoked only after the prior specification's review modal. Build one dedicated coordinator and exactly one `DB::transaction` for the whole batch; do not chain the existing unitary services' own public methods (each of which opens its own transaction) — descend their proven logic into internal collaborators/repositories that participate in this single external transaction instead.
- Before any write: validate the sensitive proof, the effective Filial against the operator's authorized scope, the payload's shape, and domain invariants. Lock physical targets in this deterministic order: `caracteristicas`, `precos`, `colunasprecos`, `produtos`, `produtoscargos`. Verify every target's `expected_revision` before writing anything.
- Revision tokens: reuse the existing revision columns already present for `produtos` and `caracteristicas`. For `colunasprecos`, `produtoscargos` and `precos` (which have no such column), canonically sign key, existence and the relevant fields — including an expected-absence signature for insert-when-not-existing cases.
- Any revision mismatch aborts the entire batch and returns every divergent target with its expected and actual revision, as a single aggregated conflict response; nothing is written and nothing is auto-merged or auto-overwritten.
- Idempotency: a request identity (UUID) plus a canonical hash of the normalized payload. A dedicated internal control keyed by this pair: the same identity with the same hash replays the previously computed result without re-executing any write or producing new audit entries; the same identity with a different hash is rejected; concurrent identical requests converge to one outcome.
- Sensitive authorization: obtain the Gerente de Estoque proof before the transaction begins, bind it to the batch/request identity/effective Filial, and consume it exactly once inside the commit. If the session's own Operador already holds the Gerente de Estoque profile, the challenge may start in "confirm own password" mode; otherwise it requires login and password of a different authorized Gerente — either way the server authenticates and verifies the profile itself; never trust a client-declared authorizer. Never persist a password. The Operador flows through the existing trigger audit context; the Autorizador is recorded separately in the batch header and in the sensitive-operation audit event, even when Operador and Autorizador are the same person.
- New internal batch header, separate from Marketplace's own audit trail: request identity, payload hash, Operador, Autorizador, effective Filial, normalized filters/query signature, timestamp, final state, and counts by table/operation.
- Per-table before/after diffs are sourced from the already-existing append-only triggers covering `produtos`, `produtoscargos`, `caracteristicas`, `precos` and `colunasprecos`, correlated by the request identity — do not manually recompute or duplicate these diffs.
- Rejected attempts (validation, missing/expired/reused/wrong-scope proof, conflict) produce no diffs. Authorization attempts (successful or not) land in the existing sensitive-operation audit log. Technical failures land in structured logs, never containing credentials or the sensitive proof's raw value.
- Mutation semantics, precisely, reusing the domain rules already fixed for Promoções and Cargo:
  - **Coluna de Preço**: Valor 0 physically removes the existing `colunasprecos` row for that identity; a non-zero Valor inserts or updates Valor/Validade; Margem is never persisted, only derived.
  - **Vínculo de Promoção**: linking or unlinking a Promoção to a Característica + Faixa is one single mutation of `precos.promocao` for that shared identity, regardless of how many visual rows the preview showed as affected — never one write per row. Unlinking only nulls the reference; it never touches the Promoção's own cadastro, nor the promotional column's Valor/Validade. If removing a promotional Valor leaves a non-null `precos.promocao` without an effective price, surface this as an explicit warning in the result rather than silently correcting it.
  - **Desconto por Cargo**: persists at the `Produto + Cargo` identity. An empty/blank input normalizes to a persisted zero, never a deletion; physical exclusion of a `Produto + Cargo` record remains its own explicit action, reusing the operation already implemented in Cadastro de Produtos, not reinvented here. Reject (do not silently ignore) any Cargo mutation in a batch when Preços por Cargo is disabled for the relevant Filial.
  - **Produtos / Característica**: field changes (markup, grupo, classe, marca, Faixa de Preço assignment) go through their existing revisioned repositories, checked with the same concurrency discipline as every other target in the batch.
- Do not call, enqueue or publish anything toward Marketplace, or toward Orçamentos/Contratos/Frente de Caixa/any other Vendas consumer, as a result of this commit. The only synchronous effect beyond the five tables and the audit/idempotency header is returning the batch result; the page itself, not this module, re-runs F6 afterward, preserving current filters. A failed post-commit refresh must never be treated as invalidating an already-successful commit.
- Do not introduce a price cache in this specification. If one is added later elsewhere, its key must include Produto, Filial, Faixa/tabela, Cliente/Cargo, Promoção/data and catalog revision — this specification must not create any read path that would violate that future requirement by caching without those dimensions.
- The canonical command accepted here is exactly the shape the prior specification produces (request identity, query signature, ordered canonical operations, expected row revisions, effective Filial); this specification's scope is validating and persisting that command, not redefining its shape.

## Testing Decisions

- The highest and primary seam is the commit operation's own public interface, exercised through integration tests against real PostgreSQL — triggers, idempotency and concurrency behavior cannot be proven against a local/SQLite substitute; treat any such substitute as structural-only, never as evidence of parity, exactly as the official price engine's own testing convention already establishes.
- Cover: full successful commit spanning every mutation kind in one batch; induced failure at the first, middle and last group proving complete rollback of all five tables; two concurrent commits with overlapping targets resolving to exactly one winner and a complete conflict list for the other, with nothing written by the loser; repeating the same request identity and payload hash producing the same result with zero new writes or log entries; the same request identity with a different payload hash rejected; missing, expired, already-consumed, wrong-Filial or wrong-batch proof rejected; the Gerente-self-password flow and the delegate-login-and-password flow, both verifying the resulting profile server-side; Promoção link persisting as one shared mutation for a Característica + Faixa touched by multiple visual rows; Promoção unlink leaving the cadastro and the promotional column untouched; an orphaned/ineffective Promoção link flagged rather than silently fixed; Coluna de Preço Valor 0 physically removing the row versus non-zero upserting it; Cargo batch rejected when the parameter is off; Cargo empty input normalized to zero, never deleted; the audit header plus trigger-sourced diffs reconstructing Operador, Autorizador, Filial, filters and every table's changes; zero calls to any Marketplace service, repository or job; post-commit F6 refresh preserving filters, and a simulated refresh failure not invalidating the already-successful commit.
- Reuse the existing unitary price/Cargo write services' own tests as prior art for the underlying SQL/business-rule correctness; do not re-prove that logic here — assert only that this coordinator composes it correctly inside the batch's transaction, locking, revision-check, idempotency and audit guarantees.
- Add a timing/performance assertion (or documented manual measurement) against the fixed budget: pré-validação and gravação completing within 15 seconds for the largest real batch, except when an explicit concurrent-block response is returned instead.

## Out of Scope

- Redefining the canonical command's shape or the prior specification's local proposal/preview computation.
- Building the F6 consulta, the three-grid shell, or the local editing/selection UI.
- Reprecificação of any already-persisted Orçamento, Contrato, Venda, parcela, reserva, comissão, cashback, frete or documento fiscal.
- Publishing events, enqueuing jobs, or calling any Marketplace service, repository or job.
- Building the Cadastro de Contratos, a future Frente de Caixa, or wiring them to consume this module — they remain future, separate consumers of the official price engine.
- Introducing a price cache.
- Changing the physical exclusion flow for `Produto + Cargo` already implemented in Cadastro de Produtos.
- Fixing or altering Delphi's legacy commit behavior.

## Further Notes

- This is the fourth and last of four incremental specs from the completed Manutenção de Preços wayfinding map. It depends on the canonical command shape produced by the third specification (Operações locais, simulação e modal F8) and on the official price engine from the first.
- The map's own release criteria apply here in full: 100% of the golden case matrix passing, no silent overwrite under concurrency, atomicity and idempotency proven by induced-failure and repetition tests, audit reconstructing the full batch (Operador, Autorizador, Filial, diffs), zero Marketplace calls, a manual homologation of at least one real batch by an Usuário de Estoque before release, and then releasing the complete feature at once to everyone who already has module access — no pilot list, no feature flag.
- The authoritative terminology comes from the ERP domain glossary: Característica de Produto, Faixa de Preço, Coluna de Preço, Valor de Preço, Preço Efetivo na Filial and Desconto por Cargo remain distinct concepts throughout the commit's mutation semantics.
- Marketplace remains a separate context in both directions; this specification shares no code, transaction, event or audit trail with it.
