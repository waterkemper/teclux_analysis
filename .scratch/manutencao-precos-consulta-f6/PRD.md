# Consulta F6, filtros, três grids e exportação da Manutenção de Preços interna

Status: ready-for-agent
Label: ready-for-agent

## Problem Statement

Usuários de Estoque precisam consultar, de uma só vez e sem paginação, todos os Produtos elegíveis de um filtro comercial (Fornecedor, situação, estoque, Promoção, Nota Fiscal de Entrada, movimentação, Característica/Grupo/Classe/Marca/Lista Padrão) para revisar seus preços, colunas de preço e descontos por Cargo lado a lado, antes de decidir qualquer alteração. Hoje essa tela só existe no Delphi (`Estoque → Manutenção de Preços`), misturada no mesmo formulário e data module com a Manutenção de Preços de Marketplace — um contexto comercial diferente que não deve ser absorvido pela migração interna.

Sem uma consulta própria, integral e sem paginação, qualquer edição futura (fora do escopo desta especificação) trabalharia sobre um recorte incompleto ou paginado, divergindo do comportamento comprovado do Delphi, onde o usuário sempre vê e decide sobre a coleção inteira filtrada.

## Solution

Criar uma página interna nova em Estoque, "Manutenção de Preços", com duas abas: **Filtros** e **Dados**. A aba Filtros reúne todos os critérios comprovados no Delphi (Produto/Característica, Fornecedor, situação, compostos, estoque, Promoção, movimentação, nota fiscal de entrada, alteração de preço, coluna e Filial de referência). O comando **Gerar F6** executa uma consulta integral própria do módulo interno — sem paginação, sem simulação, sem qualquer campo ou tabela exclusiva de Marketplace — e abre automaticamente a aba Dados.

A aba Dados apresenta três grids sincronizados por linha e por rolagem vertical, com divisores redimensionáveis, representando a mesma coleção de três ângulos: identificação do Produto, classificação/custo/formação comercial, e colunas de preço e Cargos (exibidas dinamicamente, uma tripla de campos por Coluna de Preço ativa e uma tripla por Cargo ativo, na mesma ordem e nomenclatura que o Delphi já usa). Toda a coleção é carregada de uma vez e renderizada com virtualização de linhas, já que não existe hoje nenhuma virtualização no grid genérico do Laravel — esta especificação introduz essa capacidade.

A consulta é somente leitura: não marca linhas para alteração, não edita valores, não abre modal de revisão e não persiste nada. Essas capacidades pertencem às especificações seguintes (Motor de Propostas e Commit F8). Esta especificação também cobre exportação da coleção consultada e o desempenho mínimo exigido para o volume real do catálogo.

## User Stories

1. As a Usuário de Estoque, I want a dedicated Filtros tab for Manutenção de Preços, so that I can compose a commercial filter before querying.
2. As a Usuário, I want to filter by Item de Produto, Produto, Característica, Grupo, Classe, Marca, Promoção, CST, CSOSN and Lista Padrão, so that I can narrow the catalog by any proven legacy dimension.
3. As a Usuário, I want to filter by Fornecedor, so that I can review prices for one supplier's assortment.
4. As a Usuário, I want independent situação filters (ativo/inativo, em linha/fora de linha, com/sem montagem, brinde/não brinde, disponível/não disponível no site), so that marking both, neither, or only one side behaves exactly like the legacy screen.
5. As a Usuário, I want a composto filter (todos, somente compostos, somente não compostos), so that I can isolate composed Products when needed.
6. As a Usuário, I want a "somente com estoque" filter considering stock across all Filiais, so that zero-stock Products can be excluded from a maintenance round.
7. As a Usuário, I want a Promoção filter with three states (fora de promoção, em promoção, todos) evaluated against the effective pricing Filial, so that promotional status matches production behavior.
8. As a Usuário, I want to additionally filter by a specific named Promoção, so that I can review only Products linked to it.
9. As a Usuário, I want a movimentação filter (Filial, tipo de movimento, período), so that I can find Products moved in a given window, with either end of the date range optional.
10. As a Usuário, I want a nota fiscal de entrada filter (Fornecedor/tipo, série, número, período), so that I can find Products received in specific entradas, with either date optional and série/número dependent on the chosen Fornecedor.
11. As a Usuário, I want a price-alteration filter requiring both a start and end date, so that I only see Produtos whose Coluna de Preço changed within an explicit window.
12. As a Usuário, I want to choose which Coluna de Preço is the reference for filtering, so that selecting it never silently excludes Produtos that lack a value in that column.
13. As a Usuário, I want to mark preços diferenciados por Filial and pick that Filial explicitly, so that the query resolves Coluna Normal/Promocional for that Filial instead of the Filial Base.
14. As a Usuário, I want all filter blocks combined with AND, so that the result matches exactly the intersection of every filled criterion.
15. As a Usuário, I want each filter's own internal include/exclude connectors preserved, so that composing multiple values inside one block behaves like the shared filter builder elsewhere in the ERP.
16. As a Usuário, I want Gerar F6 to run only from the Filtros tab and automatically open Dados, so that the workflow matches the legacy two-step flow.
17. As a Usuário, I want the query to return the entire filtered collection in one response, with no page/per_page/last_page metadata, so that I always work over the complete result like the legacy screen.
18. As a Usuário, I want an empty result to be a normal, successful outcome, so that a strict filter is not treated as an error.
19. As a Usuário, I want the result ordered by código visual, with description as a stable tiebreaker, so that navigation and comparisons are predictable.
20. As a Usuário, I want the previous result to remain visible while a new F6 runs, so that I am not staring at an empty screen during a requery.
21. As a Usuário, I want to cancel an in-flight F6, so that a long-running query does not block me from adjusting filters.
22. As a Usuário, I want a canceled or failed F6 to preserve the prior result, so that I never lose a working collection to a failed retry.
23. As a Usuário, I want the Dados tab to show loading progress (current stage and row count when available), so that I know a large query is progressing.
24. As a Usuário, I want three synchronized grids (identificação; classificação/custo/formação; colunas de preço e Cargos), so that I can compare every relevant fact about a Produto without switching screens.
25. As a Usuário, I want navigating, clicking or scrolling in any grid to move the same active row in the other two, so that the three views always represent one logical record.
26. As a Usuário, I want vertical scroll synchronized across the three grids while horizontal scroll stays independent per grid, so that wide columns in one pane do not disturb the others.
27. As a Usuário, I want resizable dividers between the three grids, persisted for my session, so that I can allocate width to whichever pane matters most right now.
28. As a Usuário, I want the third grid to start wider than the others, so that its many price/Cargo columns have room by default.
29. As a Usuário, I want arrow keys to move the active row across all three grids and keep it visible, so that keyboard navigation feels continuous.
30. As a Usuário, I want fixed column headers while scrolling vertically, so that I never lose context of what a column means.
31. As a Usuário, I want the first grid to show Característica/Produto code, Item code, description, grade 1/2 values (when the grades parameter is enabled) and total stock, read-only, so that I can identify each row unambiguously.
32. As a Usuário, I want the second grid to show Referência, Grupo, linked Promoção, Classe, Marca, curva ABC, CST, CSOSN, last purchase date and value, average cost, last purchase with ICMS, prices with/without ICMS and pre-tax sale price, so that I have full commercial and cost context per row.
33. As a Usuário, I want the second grid's current price fields to reflect the same Preço Efetivo na Filial the official price engine computes for the reference Filial and today's date, so that this consultation never shows a value the engine would disagree with.
34. As a Usuário, I want the third grid to start with markup, computed markup and computed preço de venda, then an Alterar indicator column, so that the layout matches the proven legacy order.
35. As a Usuário, I want one Valor/Margem/Validade triple per active Coluna de Preço, titled with that column's own name, so that I can compare every configured price column for the row.
36. As a Usuário, I want one computed-price/Margem/Desconto triple per active Cargo, titled with that Cargo's own name, appearing only when Preços por Cargo is enabled, so that role-based pricing is visible alongside regular columns.
37. As a Usuário, I want grade 1/2 columns and their titles to follow the Característica's configured axis labels, and to appear only when Usar Grades Produtos is enabled, so that grade-specific catalogs are represented correctly.
38. As a Usuário, I want the Alterar column rendered in this consultation even though marking/editing is not yet interactive here, so that the layout is already correct for the next specification that adds editing.
39. As a Usuário, I want the entire queried collection to participate in scrolling without pagination, using row virtualization so the browser never renders thousands of off-screen DOM rows, so that the page stays responsive on large results.
40. As a Usuário, I want to export the queried collection (not any unsaved local change), clearly distinct from a future export of pending proposals, so that I can share or archive a snapshot of what F6 returned.
41. As a Usuário, I want exported data to reflect exactly the columns visible in the three grids, including the dynamic per-Coluna/per-Cargo columns, so that the export is a faithful copy of what I reviewed.
42. As a Usuário de Estoque, I want to open this module only if I have access to Estoque → Manutenção de Preços specifically, so that access is scoped like every other Estoque screen.
43. As a Usuário without access, I want the page and its endpoints to reject me consistently (page, F6 and any catalog lookup), so that hiding a button is never the only protection.
44. As a Usuário, I want Fornecedor, Filial and Filial diferenciada filters validated against my authorized Filial scope, so that I cannot query data outside my access even by editing the request.
45. As a maintainer, I want this consultation to reuse the existing neutral product/supplier filter compilers and grid/export infrastructure already used elsewhere in Estoque, so that filter semantics and export behavior stay consistent across the ERP.
46. As a maintainer, I want this consultation to reuse the official Resolvedor de Preço Corrente for the second grid's current price, batched to avoid one query per Produto, so that price logic is never duplicated.
47. As a maintainer, I want the per-Coluna and per-Cargo wide projection in the third grid built by its own batched query (not by looping the price engine once per column/Cargo), so that the read path scales with the collection size, not with the number of active columns and Cargos.
48. As a maintainer, I want this module to share zero code, types or routes with Marketplace Price Maintenance, so that the two contexts never regress each other.
49. As the business, I want a documented performance budget (F6 completing in a bounded time for the largest real dataset, first usable render shortly after the response, and smooth scrolling/navigation across the three grids), so that the interface remains usable at production scale.
50. As the business, I want export to run outside the critical path of the main query/render interaction, so that generating a spreadsheet never blocks browsing the grids.

## Implementation Decisions

- Build a new deep module, **Consulta de Manutenção de Preços Interna**, exposing one operation: given normalized filter criteria and the requesting user's authorized scope, return a single coherent query snapshot. The page never assembles its view from multiple partial endpoint responses.
- The snapshot contains: the query signature (for later "filters changed, results are stale" detection, owned by the shell built in this spec), the effective reference Filial, the ordered list of Produto rows for grid 1 and grid 2's static fields, and, per row, the dynamic Coluna de Preço and Cargo projection for grid 3.
- Register a new route and page under Estoque, distinct from Consulta de Estoques and Análise de Estoques, guarded by its own module-access middleware/service pair and its own `acessosmodulos` catalog entries (index capability plus room for future capabilities), following the existing Estoque screen convention exactly. Only the `view` capability (open the page, load catalogs/parâmetros, run F6, browse the grid) is implemented in this spec — no `prepare`/`commit` behavior exists yet.
- Build a dedicated filter compiler and repository for this module's F6, composing the already-existing neutral product filter compiler (11-tab full set, reused as-is for Produto/Característica/Grupo/Classe/Marca/Promoção/CST/CSOSN/Lista Padrão) and the neutral supplier filter compiler, plus new, module-owned logic for: situação pairs (both/neither = "all", either alone = that condition; fora-de-linha honoring the proven `OR` between Produto and Característica, not an `AND`), composto tri-state, "somente com estoque" summed across all Filiais, Promoção tri-state evaluated at the effective pricing Filial (never a Marketplace account Filial), movimentação with either date open, nota fiscal de entrada with either date open and série/número gated by Fornecedor, and price-alteration requiring both dates. Do not reuse the Marketplace filter compiler, its account/alias concepts, or its Promoção/estoque/movimentação semantics — they diverge on purpose (documented divergences: fora-de-linha `OR` vs `AND`, stock scoped to Marketplace account Filial vs. all Filiais, movimentação/nota date pairs required vs. open-ended).
- The active tab set for this screen's product filter is the full 11-tab set plus Lista Padrão; Modelo, Especificação, Localização, Lotes, Atributos, NCM and Serviços are not part of F6's filtering contract in this spec (no proven legacy condition found for them here).
- Grid 1 and grid 2's static columns are fixed and read-only, matching the field lists in the User Stories above; grid 1's grade 1/2 columns and grid 2 present regardless of row content, hidden entirely when Usar Grades Produtos is off.
- Grid 2's current price fields come from one batched call to the official Resolvedor de Preço Corrente (from the prior "Motor oficial" specification) per query, using the effective reference Filial and the server's current date, with no Cliente/Cargo context — this is a generic browsing price, not a commercial simulation for a specific customer.
- Grid 3 is dynamic: for each currently active Coluna de Preço, emit a Valor/Margem/Validade column triple titled with that column's configured name; when Preços por Cargo is enabled, for each active Cargo emit a computed-price/Margem/Desconto triple titled with that Cargo's name — same ordering and naming convention as the legacy screen (columns first, then Cargos). Build this projection with its own batched query across the queried Produtos, the active Colunas de Preço and the active Cargos — do not call the price engine once per column or per Cargo per Produto.
- Grid 3 also renders markup, computed markup, computed preço de venda and the Alterar indicator column ahead of the dynamic triples, as a static, non-interactive presentation in this spec. Toggling Alterar, editing any value, comparing current-vs-proposed, undo/redo, validation and conflict indicators belong to the next specification (Motor de Propostas) and must not be built here — render the column, but it carries no interaction yet.
- Shell: two tabs, Filtros and Dados; Gerar F6 lives only in Filtros and switches to Dados on success. The command bar in Dados shows Gerar F6 and reserves visual space for the future batch-operation/undo/summary/F8 controls, but those controls are out of scope here and must not be wired to any behavior yet.
- Three grids render from the same in-memory snapshot, share one active-row concept, and are visually reordered with resizable dividers (third grid starts widest). Vertical scroll position is mirrored across all three; horizontal scroll stays per-grid. Fixed headers throughout.
- Introduce row virtualization for all three grids as new infrastructure — no existing component in this codebase virtualizes rows today (the closest precedent, Marketplace Price Maintenance, renders every row as real DOM rows with no pagination and no virtualization). Choose an approach compatible with the existing table/grid stack and with three independently-scrollable-but-vertically-synced panes.
- Reuse the existing generic ERP grid/export/preference infrastructure for column layout persistence and spreadsheet export, with a catalog and dataset owned by this module (not the Marketplace catalog/dataset). Export always reflects the queried snapshot currently loaded; exporting unsaved local proposals is explicitly a different, future capability once the next specification introduces local edits.
- Validate the effective reference Filial, the differentiated-price Filial and the movimentação Filial against the requesting user's authorized Filial scope on every request; an elevated profile does not widen this scope.
- Do not import, call or depend on any Marketplace-namespaced module, type, route, filter compiler, repository, dataset or catalog. Marketplace may depend on shared neutral infrastructure; the dependency never runs in the other direction.

## Testing Decisions

- Good tests here assert observable query behavior — given filter criteria and an authorized scope, what rows/fields/order come back — not internal SQL shape or private compiler methods.
- Backend: Feature tests against the F6 endpoint, following the existing Estoque screen Feature-test convention (Consulta de Estoques / Análise de Estoques). Cover: each filter block individually and in combination (AND across blocks); situação pair semantics (both/neither = all, either alone = filtered, especially the fora-de-linha `OR` behavior); composto tri-state; estoque summed across Filiais; Promoção tri-state at the effective pricing Filial; movimentação and nota fiscal de entrada with one or both dates; price-alteration requiring both dates; Coluna/Filial selection never dropping valueless Produtos; ordering by código visual with description tiebreak; empty result as success; full result with no pagination fields; unauthorized Filial rejected even when requested explicitly; a user without module access rejected on page, F6 and any catalog lookup endpoint; no Marketplace table, job or service invoked.
- Add a batched-query-count assertion (or equivalent) proving grid 2's price lookup and grid 3's per-Coluna/per-Cargo projection do not degrade into one query per Produto or per column/Cargo as the result set and active-column/Cargo count grow.
- Frontend: component tests for the new shell/page, following the existing `ErpPreferenceDataGrid`/`EditableDataGrid`-based screen conventions. Cover: Gerar F6 from Filtros switches to Dados; cancel preserves the prior result; active-row navigation and vertical scroll stay synchronized across the three grids while horizontal scroll does not; divider resize persists for the session and the third grid starts widest; grade columns appear only when the parameter is enabled; Cargo columns appear only when Preços por Cargo is enabled and are titled with the Cargo's name; Coluna de Preço triples are titled with the column's name and appear in the same order as active columns; the Alterar column renders without any interactive behavior; export produces the same columns visible in the grids for the currently loaded snapshot.
- Add a virtualization-specific test (or lightweight rendered-node-count assertion) proving that with a large synthetic result set the DOM does not hold a real row per off-screen record, since this is new infrastructure with no existing precedent to inherit confidence from.
- Reuse existing Estoque filter-compiler and Resolvedor de Preço Corrente tests as prior art/fixtures where the same underlying rules apply; do not re-assert engine correctness already proven by the prior specification's golden cases — assert only that this module calls it correctly and batches it.

## Out of Scope

- Marking rows for alteration ("Alterar"), any local editing of values, copy/adjust/clear/recalculate operations, history/undo/redo, computed current-vs-proposed comparison, validation, conflict indicators, and the F8 review modal — all belong to the next specification (Motor de Propostas, simulação e modal F8).
- Any persistence, sensitive authorization, optimistic concurrency, idempotency or audit trail — belongs to the atomic commit specification.
- Building, extending or touching Marketplace Price Maintenance's service, repository, filter compiler, grid, dataset, types, page or export.
- Building Modelo, Especificação, Localização, Lotes, Atributos, NCM or Serviços as filter dimensions — not proven in the legacy query this spec migrates; a future spec may add them with its own evidence.
- Contexto de Nota Fiscal de Entrada beyond what already filters the collection (this spec does not build a new nota fiscal de entrada screen).
- Any change to the official Resolvedor de Preço Corrente's contract; this spec only consumes it in batch.
- Deciding the exact virtualization library/technique implementation details beyond "introduce row virtualization compatible with the three-pane synchronized shell" — the specific approach is an implementation choice within this spec's scope, not a pre-selected dependency.
- Implementing code, running migrations/builds/tests or modifying Delphi outside what this specification directly requires to deliver its own scope.

## Further Notes

- This is the second of four incremental specs from the completed Manutenção de Preços wayfinding map, and depends on the first (Motor oficial e casos dourados de cálculo) for grid 2's current price. After this spec's contracts stabilize, it may proceed in parallel with the transactional foundation of the fourth (Commit F8) spec; the third spec (Operações locais, simulação e modal F8) depends on this one's data contracts.
- The authoritative terminology comes from the ERP domain glossary: Característica de Produto, Faixa de Preço, Coluna de Preço, Valor de Preço, Preço Efetivo na Filial and Desconto por Cargo are distinct concepts and must be used precisely.
- The dynamic per-Coluna/per-Cargo columns in the third grid are a raw, side-by-side catalog projection (every active column's own configured Valor/Margem/Validade, every active Cargo's own computed price/Margem/Desconto) — this is different from the single resolved Preço Efetivo the official price engine returns for one commercial scenario, and both are legitimately present on the page for different reasons (grid 2 shows the one current effective price for browsing; grid 3 shows every configured column/Cargo for comparison and future editing).
- No virtualization infrastructure exists yet anywhere in this codebase; treat it as new, reusable infrastructure rather than a page-specific hack, since the next two specs' grids will need the same capability.
- Marketplace Price Maintenance remains a separate context and must not be imported by this module in either direction beyond shared neutral infrastructure.
