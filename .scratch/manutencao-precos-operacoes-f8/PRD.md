# Operações locais, simulação e modal F8 da Manutenção de Preços interna

Status: ready-for-agent
Label: ready-for-agent

## Problem Statement

A Consulta F6 da Manutenção de Preços interna (já implementada) devolve toda a coleção filtrada em três grids sincronizados, mas é somente leitura: a coluna "Alterar" é hoje um checkbox estático e desabilitado, e não existe nenhum estado de seleção, edição, operação em lote, histórico ou prévia. O Usuário de Estoque precisa marcar linhas, editar valores de Coluna de Preço e de Cargo diretamente, copiar uma coluna para outra, aplicar percentual/validade, limpar uma coluna, recalcular projeções, desfazer, e revisar tudo antes de decidir gravar — exatamente como o Delphi legado permite, mas com histórico/desfazer que o legado não tem e com intenções explicadas em vez de ignoradas silenciosamente.

Sem essa camada, qualquer tentativa de editar preços em lote seria construída sobre a grade atual sem um modelo de sessão, seleção e prévia coerente — arriscando reproduzir a mistura Delphi de seleção, buffers invisíveis e projeções num único estado difícil de auditar.

## Solution

Tornar interativos os três grids já existentes da Consulta F6, introduzindo uma **sessão local de edição** inteiramente em memória no cliente, espelhada por um endpoint de simulação no servidor que usa o mesmo contrato para qualquer prévia. Nenhum comando desta especificação grava no banco — persistência continua reservada a uma especificação futura de commit atômico (F8/F5), que esta entrega apenas prepara: o resultado observável aqui é um **comando canônico** revisável, pronto para ser submetido quando essa especificação existir.

A coluna "Alterar" passa a ser um checkbox real, com cabeçalho tri-estado (marcado/desmarcado/parcial) e contagem "selecionadas / total" sobre **toda** a coleção do F6, não apenas a janela renderizada pela virtualização. Comandos em lote (aplicar percentual/validade, copiar coluna, limpar coluna, recalcular) atuam somente sobre linhas selecionadas; edição manual de célula não exige seleção. Operações são cumulativas com histórico e desfazer; a prévia mostra valor original, valor proposto e o motivo de cada linha (`alterada`, `sem mudança`, `ignorada`, `erro`). O comando **Revisar e gravar F8** abre um modal que resume alterações, linhas ignoradas, erros e conflitos, chamando o servidor para recalcular a mesma prévia — o modal fica desabilitado enquanto houver erro ou conflito não resolvido, e termina pronto para submissão, sem persistir.

## User Stories

1. As a Usuário de Estoque, I want to check a real Alterar checkbox per row, so that I can mark which rows a batch command should affect.
2. As a Usuário, I want a header checkbox showing marked, unmarked or partial state with a "selecionadas / total" count over the entire F6 result, so that I always know the true selection size regardless of scroll position.
3. As a Usuário, I want "Selecionar todos" to select every row of the current F6 result, including rows not currently rendered by virtualization, so that batch commands reach the full filtered collection.
4. As a Usuário, I want unmarking a row to leave its already-applied proposals intact, so that selection only controls future operations, not past ones.
5. As a Usuário, I want to edit a Coluna de Preço's Valor directly in the grid without selecting its row, so that a quick single-cell correction does not require the batch selection ritual.
6. As a Usuário, I want an edit to a Valor shared by Característica + Faixa + Coluna to reflect on every other row sharing that identity, so that shared pricing configuration stays consistent, exactly like the official price model.
7. As a Usuário, I want Cargo discount edits to propagate exactly as already decided for Cargo pricing, so that role-based pricing stays consistent with the rest of the system.
8. As a Usuário, I want "Aplicar percentual e/ou validade" to require a source column and act only on selected rows, so that the operation is scoped and explicit.
9. As a Usuário, I want a positive percentage to increase the column's Valor and a negative one to decrease it, computed over the currently proposed value (not necessarily the original), so that stacked operations behave predictably.
10. As a Usuário, I want an empty or zero percentage to leave the price unchanged, and an empty validity to leave validity unchanged, so that I can adjust just one of the two independently.
11. As a Usuário, I want the proposed Valor to pass through the existing rounding/múltiplo resolution (Produto → Grupo → Classe → parâmetro global), so that proposed prices already respect company policy before I ever see them.
12. As a Usuário, I want "Copiar coluna" to require a different source and destination column, so that copying a column onto itself is rejected outright.
13. As a Usuário, I want copying to apply the currently proposed source value (optionally adjusted by a percentage) to the destination, and to substitute validity only when I provide one, so that I can compose a copy with an adjustment in one step.
14. As a Usuário, I want a source column with zero or empty Valor to leave the destination row alone and appear in the preview explicitly as "ignorada — origem sem preço", so that I understand why a row didn't change instead of it silently vanishing like in the legacy screen.
15. As a Usuário, I want "Limpar coluna" available for the Normal column and for any additional/promotional column, so that clearing behaves consistently across all column types.
16. As a Usuário, I want clearing to require its own confirmation showing the column, total selected and total that will actually lose a value, with a reinforced warning specifically when the target is the Normal column, so that an irreversible-feeling action is never one accidental click away.
17. As a Usuário, I want clearing to only prepare the proposal (value/margin/validity emptied locally), not persist anything, so that F8/F5 remains the sole persistence boundary.
18. As a Usuário, I want "Recalcular" to refresh calculated projections (computed sale price, margins, per-Cargo calculated price) from the currently proposed inputs (cost, markups, multiples, active Promotions and Cargos) without creating any persistible change when no persistible input actually changed, so that recalculation never invents a fake edit.
19. As a Usuário, I want rows where recalculation fails to be identified explicitly rather than silently skipped, so that I know exactly which rows need attention.
20. As a Usuário, I want every command to classify each affected row as alterada, sem mudança, ignorada or erro, so that the preview's language is consistent across every operation.
21. As a Usuário, I want "sem mudança" rows to never generate a persistible mutation, so that a no-op command truly does nothing.
22. As a Usuário, I want "ignorada" rows to never block the rest of a batch command, so that one bad row doesn't stall the others.
23. As a Usuário, I want "erro" rows to prevent the preparation from being considered complete until resolved or removed, so that F8 never reviews a lot with unresolved failures.
24. As a Usuário, I want operations to be cumulative — each new operation reads the current proposed value, not necessarily the original — so that stacking, e.g., a copy followed by a percentage adjustment, behaves like it would on paper.
25. As a Usuário, I want the preview to retain original value, final proposed value and the intermediate operation history for any cell touched by more than one command, so that I can understand how a value got where it is.
26. As a Usuário, I want undoing the last operation to restore exactly the state before it ran, so that mistakes are recoverable without discarding the whole session.
27. As a Usuário, I want a pending-changes summary (counts by column/command/status), so that I can gauge the size of my proposal before opening the review modal.
28. As a Usuário, I want error, changed and conflict counters with quick filters ("Somente alterações", "Com erros", "Com conflitos") above the three grids, so that I can jump straight to what needs attention.
29. As a Usuário, I want clicking a counter to navigate to its first occurrence across the synchronized grids, so that finding a problem doesn't require manual scrolling.
30. As a Usuário, I want cell- and row-level error/conflict indicators to appear consistently across all three grids for the same logical row, so that I never lose track of which row has a problem when looking at a different pane.
31. As a Usuário, I want running a new F6, changing filters, switching the reference Filial, or leaving the page with pending changes to force an explicit choice between continuing the current session or discarding it, so that proposals are never silently lost or silently carried into an unrelated query.
32. As a Usuário, I want "Revisar e gravar F8" to open a modal — not a third tab — summarizing changes, ignored rows, errors, conflicts and the authorization that will eventually be required, so that review has a dedicated, focused surface.
33. As a Usuário, I want F8 disabled while any unresolved error or conflict exists, so that an incomplete or invalid proposal can never reach review as if it were ready.
34. As a Usuário, I want the modal's summary to be recomputed by the server from the same operations I applied locally, not trusted purely from client-side math, so that what I'm about to submit matches what the server will actually process later.
35. As a Usuário, I want the preview to clearly separate persistible entries (Coluna de Preço Valores, Faixa/Produto assignment, Cargo discounts) from recalculated projections, so that I never mistake a derived number for something that will be written to the catalog.
36. As a maintainer, I want a single Motor de Propostas interface — given the current query's signature and an ordered list of canonical operations, return a preview — consumed identically by local instant feedback and by the server, so that the rules exist in exactly one place.
37. As a maintainer, I want the canonical operation list (select, edit, copy, adjust, clear, recalculate) and their composition order to be the one source of truth for both the client's optimistic preview and the server's authoritative recompute, so that they cannot drift apart.
38. As a maintainer, I want "aplicar percentual"/"copiar coluna" to operate arithmetically on the column's own Valor de Preço using the proven legacy formula (value × (1 ± percentual/100)) through existing rounding/múltiplo resolution, distinct from "recalcular", which refreshes calculated projections through the official price engine's existing markup-as-discount-over-effective-price formula — so that the two different "markup" meanings already coexisting in this codebase are never conflated by a new operation.
39. As a maintainer, I want the canonical command produced by this specification (request identity, query signature, ordered operations, expected row revisions, effective Filial) to be exactly the shape the future atomic-commit specification will accept, so that the next specification is a pure "submit and persist" layer, not a redesign.
40. As a Usuário, I want a `view`-holder to also have a `prepare` capability (select, edit, simulate, review) without any sensitive authorization, so that preparing a proposal never requires the elevated proof that only the future commit step will demand.
41. As a maintainer, I want the grid catalog and export to be extended to cover the Alterar indicator and the dynamic per-Coluna/per-Cargo values (today silently omitted from export), so that a snapshot of the current session — clearly labeled as a preview, distinct from a plain F6 export — can be shared.
42. As a Usuário, I want exporting the current local session (with pending proposals) to be a visibly different action from exporting a fresh F6 query result, so that I never confuse a working draft with the queried catalog state.
43. As a maintainer, I want selection and per-cell proposal state keyed by row identity (produto_codigo + caracteristica_codigo), not by array index, so that selection and proposals survive re-sorting or partial re-render and are never silently misapplied to the wrong row.
44. As a tester, I want the golden cases already defined (select-all beyond the rendered window; copy-then-adjust chaining; zero-source copy ignored with reason; validity-only and percentage-only application; Normal-column clearing warning; unmark preserving a proposal, undo restoring it; manual edit propagation by shared identity; recalculate touching only projections when no persistible input changed; new F6 or Filial change never silently discarding proposals) proven as automated tests, so that this specification's behavior matches what was already agreed.

## Implementation Decisions

- Introduce a local editing session, entirely client-held, layered over the existing F6 result (`rows`/`meta` already returned by the Consulta service). No command in this specification writes to the database; F8/F5 persistence is the exclusive concern of a future specification.
- Selection is a set of row identities (`produto_codigo` + `caracteristica_codigo`), independent from the existing `activeRowIndex` navigation state already implemented for cross-grid synchronization. Do not key selection or proposals by array index — F6 results are not guaranteed stable-order across a re-query, and index-based state would silently misattribute an edit to the wrong row.
- Replace the existing static, disabled "Alterar" cell (and the TypeScript type presently pinning it to the literal `false`) with a real, interactive checkbox bound to the selection set; widen the row type's `alterar` field from `false` to `boolean`. The existing test that locks the current non-interactive behavior must be intentionally superseded by this specification's own tests, not left in place as a contradictory regression guard.
- Header selection control has three states (all/none/partial) and shows a live "selecionadas / total" count computed over the entire F6 result set held in memory, not the virtualized render window.
- Model the proposal state as: for each touched cell, the original value, the current proposed value, and an ordered list of the operations that touched it (for the "intermediate history" requirement). Operations are cumulative: each new operation reads the current proposed value of its targets, not necessarily the original. When multiple operations target the same cell, the latest wins for the final value, and undo removes only the most recent operation, restoring the prior proposed state exactly.
- Build one shared **Motor de Propostas** contract: given the current query's signature (already returned in F6's `meta`) and an ordered list of canonical operations, compute a batch preview. The frontend may apply this locally for instant feedback, but the same contract must be recomputed server-side (a new "simular" endpoint) when opening or confirming the F8 modal — the modal's authoritative content always comes from the server recompute, never purely from client-side state.
- Canonical operations, each producing a per-row outcome of `alterada`, `sem mudança`, `ignorada` or `erro`, with a human-readable reason for `ignorada`/`erro`:
  - **Selecionar todos / Desmarcar todos** — pure selection-set mutation, over the whole result set; not itself an operation with a preview outcome.
  - **Aplicar percentual e/ou validade** — requires an explicit source column and acts only on selected rows. Proposed Valor = current proposed Valor × (1 + percentual/100); empty or zero percentual leaves the Valor unchanged; empty validity leaves validity unchanged; a supplied validity replaces it outright. Route the resulting Valor through the existing rounding/múltiplo resolution (Produto → Grupo → Classe → parâmetro global) before it becomes the new proposed value.
  - **Copiar coluna origem → destino** — requires source ≠ destination; acts on selected rows. Assigns the currently proposed source Valor to the destination, optionally passing it through the same percentage-adjustment formula as above before assignment; validity is replaced only when explicitly supplied, otherwise inherited from the source. A source Valor that is zero or empty leaves the destination row untouched and is classified `ignorada — origem sem preço` in the preview, never silently skipped.
  - **Limpar coluna** — acts on selected rows; empties Valor, Margem and Validade locally for the target column (Normal or any additional/promotional column). Requires its own confirmation step showing the target column, total selected and total that will actually lose a configured value, with a visually reinforced warning when the target is the Normal column. Confirming only stages the proposal — it does not persist.
  - **Edição manual de célula** — editing a Coluna de Preço Valor or a Cargo discount directly never requires the row to be selected. A shared-identity edit (Característica + Faixa + Coluna) reflects on every other row sharing that identity, matching the official pricing model; Cargo edits propagate per the already-decided Cargo pricing rules.
  - **Recalcular** — pure projection over selected rows (or, if none selected, over all rows with pending proposals — specify exactly one behavior and keep it consistent). Refreshes calculated/derived columns (computed sale price, margins, per-Cargo calculated price) from currently proposed persistible inputs (cost, markups, multiples, active Promotions, active Cargos), using the official price engine's existing markup-as-discount-over-effective-price formula for Cargo-derived calculated prices, and the existing cost-based markup formula for the computed sale price column — the same two formulas the read-only Consulta service already uses for those respective fields, never conflated with each other or with the percentage-adjustment formula above. Recalculate never creates a persistible mutation when no persistible input actually changed for a row, and explicitly flags rows where it cannot compute a result.
- Every command's preview separates persistible entries (Coluna de Preço Valor/Validade, Faixa/Produto assignment, Cargo discount) from recalculated projections (margins, computed sale price, Cargo calculated price) — projections never appear as an independently persistible change.
- Provide an explicit pending-changes summary (counts by column/command/status) and counters/quick filters for "Somente alterações", "Com erros" and "Com conflitos" rendered above the three synchronized grids; clicking a counter navigates the shared `activeRowIndex` to its first matching occurrence. Cell- and row-level indicators for changed/error/conflict state must render consistently across all three panes for the same logical row.
- Running a new F6, changing any filter, switching the reference Filial, or navigating away with pending changes must force an explicit choice between continuing the current local session or discarding it entirely — proposals never migrate automatically to a different query result, and never disappear silently either.
- "Revisar e gravar F8" opens a modal (not a third tab), populated by the server-side recompute of the current canonical operation list against the current query signature. It shows: total changes, ignored rows with reasons, unresolved errors, conflicts, and a notice that committing will require the sensitive authorization already established for this module (Gerente de Estoque) — but this specification does not implement the actual submission, persistence, authorization challenge or concurrency handling behind that eventual commit action; the modal ends at producing a reviewable, ready-to-submit canonical command. Disable the review/commit action while any error or unresolved conflict exists anywhere in the session.
- The canonical command produced here (request identity, current query signature, ordered canonical operations, expected row revisions, effective Filial) must be shaped exactly as the future atomic-commit specification will need to accept it as input — this specification's output is that command's construction and server-side validation via simulation, not its persistence.
- Extend the authorization service for this module with a `prepare`-equivalent capability (selection, editing, simulation, review) that requires only the existing `view`-level module access, with no sensitive-operation challenge — sensitive authorization is reserved for the future commit action.
- Extend the grid catalog (and the export it feeds) to include the Alterar indicator and the dynamic per-Coluna/per-Cargo values, which the catalog and export currently omit entirely. Exporting the current local session (including unsaved proposals) must be a visibly distinct action from exporting a plain F6 query result, clearly labeled as a preview/rascunho, not a persisted catalog state.
- F6 execution itself is synchronous, always — do not build or extend this specification on top of any asynchronous job/polling wrapper around F6; if the current implementation wraps F6 in an async job with polling, treat that as a pre-existing divergence to reconcile outside this specification's scope, not a contract this specification should assume, extend or rely on.

## Testing Decisions

- Good tests here assert observable session/preview behavior — given a starting F6 result, a selection and an ordered list of operations, what preview and final proposal state results — not internal reducer/state-management implementation details.
- Backend: Feature/Unit tests for the new "simular" endpoint and the shared Motor de Propostas logic, following the existing Estoque module test conventions (`ManutencaoPrecosGerarTest.php`, `ManutencaoPrecosFilterCompilerTest.php`, `ManutencaoPrecosProjectionBatchTest.php` as prior art for HTTP/unit shape). Cover every canonical operation and its row-outcome classification (`alterada`/`sem mudança`/`ignorada`/`erro`) individually and in composed/cumulative sequences; the two distinct markup formulas exercised separately and asserted by both value and applied formula/path, not value alone; rounding/múltiplo resolution applied to percentage/copy operations; "sem mudança" never producing a persistible mutation; "ignorada" never blocking sibling rows; "erro" preventing the preparation from being reported complete; undo restoring the exact prior state; a query-count/equivalent assertion proving simulation does not degrade into per-row engine calls as selection size grows.
- Frontend: component tests for the three-grid shell, extending the existing conventions (`DadosTriPane.test.tsx`, `ManutencaoPrecosVirtualization.test.tsx`). Cover: header tri-state selection and its whole-result count (including rows outside the virtualized window); Alterar checkbox now interactive, explicitly superseding the prior "non-interactive" test; manual cell edit without selection, propagating by shared identity; each batch command's confirmation flow (especially Limpar coluna's reinforced Normal-column warning); counters/quick filters navigating to the first matching row across synchronized panes; the discard-or-continue prompt firing on new F6/filter/Filial change/navigation-away with pending changes; F8 modal disabled while errors/conflicts remain, and its content matching a mocked server "simular" response rather than only client-computed state; export distinguishing a plain F6 export from a labeled session/preview export.
- Add the golden cases already defined by the prior wayfinding decision as automated cases, named by business scenario (select-all beyond render window; copy-with-adjustment chaining; zero-source copy ignored with reason; validity-only and percentage-only application; Normal-column clear warning; unmark-then-undo restoring a proposal; manual edit propagating by shared identity; recalculate touching only projections when no persistible input changed; new F6/Filial change never silently discarding proposals).
- Reuse the existing official price engine's own golden/unit tests as prior art for the two markup formulas; do not re-prove engine correctness here — assert only that this specification's operations call the correct formula for each operation and do not conflate them.

## Out of Scope

- Actually persisting any proposal, the atomic F5/F8 commit itself, sensitive-operation authorization challenge, optimistic concurrency against the database, idempotency and the audit trail — all belong to a future atomic-commit specification. This specification ends at producing a reviewable canonical command and its server-recomputed preview, not submitting it.
- Any change to the F6 Consulta contract, its filters, its route/module-access wiring beyond adding the `prepare` capability, or its underlying query/projection repositories.
- Any change to the official price engine's (`PrecoCorrenteResolver` / `LegacyProductPriceEngineRepository`) public contract; this specification only calls its existing methods.
- Reconciling or rebuilding F6's execution model (synchronous vs. asynchronous) — F6 must be synchronous; if the current implementation diverges, that reconciliation is separate work, not part of this specification.
- Building Marketplace Price Maintenance's equivalent commands, calculators, or export.
- Redesigning the shell's tabs, virtualization mechanism, or cross-grid active-row/scroll synchronization already implemented — this specification only adds selection/editing/preview state and UI on top of them.
- Implementing code, running migrations/builds/tests or modifying Delphi outside what this specification directly requires to deliver its own scope.

## Further Notes

- This is the third of four incremental specs from the completed Manutenção de Preços wayfinding map. It depends on the data contracts of the second (Consulta F6) and the engine of the first (Resolvedor de Preço Corrente), and its canonical command is the direct input contract for the fourth (Commit F8 atômico, concorrência e auditoria).
- As implemented, the Consulta F6 endpoint currently returns through an asynchronous job/polling wrapper (job id + status polling) rather than a single synchronous response. This has been confirmed as a divergence from the intended contract — F6 must always be synchronous. This specification does not fix that; flag it explicitly for whoever next touches the F6 endpoint, and do not design this specification's session/preview flow around the polling wrapper as if it were intentional.
- Two distinct "markup" formulas already coexist in the codebase and must stay distinct: a cost-based markup (`custo × (1 + markup/100)`, used for the read-only computed sale price column) and the official engine's markup-as-discount-over-effective-price (`preço efetivo × (1 − markup/100)`, used for Cargo-derived calculated pricing). Neither is the same as this specification's percentage-adjustment formula on a Coluna de Preço's own Valor (`valor × (1 ± percentual/100)`, the proven legacy formula for "aplicar percentual"/"copiar coluna"). State explicitly, per operation, which of the three formulas applies.
- The authoritative terminology comes from the ERP domain glossary: Característica de Produto, Faixa de Preço, Coluna de Preço, Valor de Preço, Preço Efetivo na Filial and Desconto por Cargo remain distinct concepts.
- Marketplace Price Maintenance remains a separate context; this specification shares no code, type or route with it.
